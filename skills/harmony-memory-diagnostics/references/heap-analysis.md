# ArkTS 堆快照与泄漏证据

## 先核对设备能力

不同系统和 debug/release 包对 profiler 的支持不同。先查已安装系统的 `hidumper` 帮助；失败时保留原始错误，不尝试 root、关闭系统保护或绕过签名。命令参考可查 [华为 HiDumper 文档](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/hidumper/)，以当前设备帮助和可观察行为为准。

已在 HarmonyOS 真机使用过的命令形式：

```bash
hdc -t <device> shell hidumper --mem <pid>
hdc -t <device> shell hidumper --mem-jsheap <pid> --gc
hdc -t <device> shell hidumper --mem-jsheap <pid> -T <tid>
```

`--gc` 是请求，命令返回不代表所有 VM 已完成回收。`-T <tid>` 限定目标线程；诊断主线程时一般 tid=pid，其他 VM 需要分别核实和采集。不要把多个 VM 的对象合计误当成单一快照。

## 建立可比的检查点

- 场景由用户指定；典型安排是操作前、若干次操作后、末尾各采一份，在相同页面且任务状态一致时取证。不将三份快照或某个轮数强制为所有任务的要求。
- 连续自然运行采样与强制 GC/快照窗口分开标记。快照会改变后续基线；想测无干预的内存走势时，应另开自然运行批次，不把快照造成的下降视作业务释放。
- 每次保存：GC 前内存、GC 请求时间和等待时间、快照请求/完成/传输时间、快照后内存、PID/TID、页面状态与后台任务状态。
- 初始用保守等待并检查设备响应；存在异步 GC 时也不能凭固定 3 秒或 10 秒宣称完成。GC 尚未稳定或设备卡顿时，不叠加更多 GC、快照或 profiler 清理。

## 导出完整快照

1. 记录当前 PID/TID，枚举输出目录中已有文件。
2. 发起一次目标线程快照，在当前设备响应可控的前提下等待新的文件出现。常见目录为 `/data/log/reliability/resource_leak/memory_leak`，文件类似 `hidumper-jsheap-<pid>-<tid>-<sequence>`；不可把路径/命名作为所有系统的固定协议。
3. 轮询新文件大小，连续多次不变后传输；仍需用解析器成功读完整 JSON 验证。超时或无权限时保存错误，不能取目录里旧文件冒充本次快照。
4. 保存源文件名、大小、哈希与命令结果；对分析缓存与原始快照分目录。数据可能包含账号、页面和业务内容，不打印 strings 全表或自动上传。
5. 不默认调用 `--clean` 或收尾追加全 VM GC。曾在真实设备上观察到 profiler clean/额外 GC 后发生 GC 相关 ThreadBlock；这是诊断风险线索，不应推广为所有 runtime 必现缺陷。必要清理先核对当前系统语义，并与正式数据分开。

## 大快照离线分析

数百 MB 的快照不要整体打印，也避免普通 JSON 加载产生多倍内存。优先 DevEco 的堆分析工具；需要脚本时可在独立 Python 虚拟环境使用 `ijson` 流式读取，`numpy` 数组/内存映射存储数值字段。不要安装到全局环境。

读取 `snapshot.meta`，按实际 `node_fields`、`edge_fields`、`node_types` 和 `edge_types` 解码，不固定字段宽度。常见结构：

- `nodes`：类型、名字字符串索引、对象 id、self_size、edge_count 等。
- `edges`：边类型、名字或元素索引、to_node；`to_node` 常为 nodes 扁平数组偏移，需要按实际节点宽度换算。
- `strings`：类型名、属性名和内容等字符串。

先做总体类型/大小汇总，再筛本场景创建并应销毁的类。不要只因“涨得最多”就把正常业务缓存当作根因。

## 从疑点到根因

1. **计数口径。** 统计实际对象实例，排除同名 closure、类构造器、原型对象。可以通过实例字段及拥有 `constructor` 属性的对象辅助识别原型，但要人工核对目标类，不能把启发式当成通用定理。
2. **追踪身份。** 同一进程、同一 profiler 跟踪周期内比较对象 ID：中期对象在末尾仍存活，比单纯计数更有力。跨进程/重新安装后的 ID 不可比较；记录是否重置过 profiler。
3. **看清理字段。** timer、controller、entity、回调是否已清空，区分“未执行 dispose”与“dispose 已执行但外部仍持有”。
4. **找强根。** 为目标建反向边索引，自目标向 GC Root 搜索，排除 weak 边。记录路径上每个对象的 id、类型、属性和边类型；大图可缓存按目标排序的边索引，避免每次全表扫描。
5. **核查所有权。** 在代码中验证全局注册表、订阅、定时器、异步任务、闭包、JSB 服务表、Native 回调等路径。存在并行路径时，切断最短路径并不代表全部引用解除。
6. **评估体量。** self_size 是浅大小；保留大小不能对重叠子图简单求和。共同阻断一组对象后新增不可达节点的体量只是图上联合保留估计，不能直接等同 PSS，外部 Native 大小也可能重复归属。

可信结论至少包含：用户可复现操作、预期生命周期、实际存活对象、强根路径、对应源码。只有计数或 PSS 时标记为疑点，并列出下一步验证手段。

## 修复后验证

按完整闭环的已授权范围实施，遵循 [repair-loop.md](repair-loop.md) 一次只修一个问题，再按所有权选择取消注册、释放订阅/任务、清理回调或合适的弱引用机制。弱值/弱键不能机械替换：确认活跃页面期间对象不会提前失效，循环引用在所用运行时可正常回收，Native 资源仍有确定性释放。

复测保持真机、版本配置、场景、重复次数、时长和快照状态一致；无法一致的条件逐项披露。检查：

- 本次场景全部有效完成；业务 UI/JSB/保存等仍按预期工作。
- 目标已关闭对象不再按操作次数线性积累，旧实例可回收，强根注册不再保留它们。
- 分别比较稳定阶段占用、峰值、结束增量和自然/GC 后走势。
- 独立未修复链路或全进程 PSS 增长仍存在时单列，不能宣称“所有内存泄漏已修复”。

真机复测证明当前问题已解除且功能正常后，将该问题单独提交本地 commit，再基于新版本继续分析其他问题。完整提交门槛、失败重试和最终批次验收见 [repair-loop.md](repair-loop.md)。
