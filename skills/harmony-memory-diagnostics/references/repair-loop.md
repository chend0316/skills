# 单问题修复、真机验证与逐项提交

## 授权和工作区

完整调用本 Skill 的任务包括编译运行、重复用户场景、取证、修复与验证后本地提交；用户已授权范围内连续推进，不为每次安装、修改或 commit 再次询问。用户给出的只读、禁止提交、设备独占或项目 Review 约束优先。未指定场景时先获取场景，再开始业务操作。

先读取目标项目规则，记录当前分支、HEAD、工作区 diff 和暂存区状态。保留已有改动，不 reset、stash 或覆盖。当前问题与已有改动重叠、无法可靠独立提交时，先完成可独立的取证，明确说明具体冲突并获取处理安排；不能把他人改动变成自己的修复。读取身份与项目要求，不擅自改 Git 身份绕过校验。

所有批次使用独立结果目录，关联代码版本、工作区补丁哈希、构建包哈希及协议。原始快照、分析缓存与日志留在本地结果目录，不默认放进源码提交。

## 问题队列

为每个独立根因维护一条记录，例如 `issues.json` 或报告表格：

| 字段 | 内容 |
|---|---|
| issue_id / 状态 | suspected、confirmed、fixing、verifying、verified、committed、blocked |
| 触发场景与影响 | 创建/退出操作、应释放对象或资源、影响量级 |
| 根因证据 | 实例/分配增长、强根或资源分配栈、源码位置 |
| 基线批次 | 代码/补丁/包哈希、真机、配置与快照 |
| 修复假设与范围 | 解除哪条持有或补哪处释放、涉及文件 |
| 验收条件 | 预期计数/有界保留、根路径、功能及内存检查点 |
| 尝试与复测批次 | 改动、结果、失败原因、新证据 |
| commit | 验证通过后产生的一个本地 commit SHA |

同一全局注册或队列造成多个类增长通常是一个问题；不同资源所有权或独立强根通常是多个问题。以根因划分，不按类名或文件数量机械拆分。优先处理证据明确、影响较大且可独立验证的问题。

同一时刻只让一个问题处于 fixing/verifying。前一个提交并交付报告后，再按所选执行节奏决定是否开始下一个，保证每个 commit 都有独立因果证据。不要为了“修完所有问题”扩大到用户场景之外或把未经证实的疑点也改掉。

## 每个问题的迭代

1. **保存当前基线。** 初次使用原版本；后续使用上一个已验证 commit。最新快照若足以重现当前根因，可复用为本问题的修复前证据；不足则补跑相同协议。
2. **写明可验证假设。** 指出哪条注册、闭包、订阅或分配持有了应释放资源，预期修改后哪些指标/根路径发生什么变化。
3. **最小修复。** 检查所有并行引用路径与活跃期行为。多个文件只有共同服务于一个根因时才同批修改。不要以强制 GC、定时清缓存、重启进程掩盖泄漏。
4. **构建并安装当前改动。** 构建失败先定位；环境故障不能算修复无效，也不能顺手混入业务提交。核对设备运行的确实是新包，而非上次安装残留。
5. **完整重跑本批多次场景。** 保持用户次数/时长与采集口径，包含前、中、后可比快照及功能状态。修复前后是不同进程时比较计数、根路径与趋势，不比较对象 ID 数值是否相同。
6. **判定效果。** 满足下一节标准才能标 verified。未通过时保留失败批次，依据新证据继续改同一问题，再次构建并复测；不提交空改动或未验证修复。
7. **生成单独 commit。** 按下一节核对内容并本地提交，立即回填 SHA。提交失败只修复提交所缺条件，不把未经提交状态写为 committed。
8. **交付本问题结果。** 按 [results-template.md](results-template.md) 输出独立报告、逐次指标表和趋势图，回填 commit SHA 与源码、验证批次和原始证据路径，立即向用户提供可访问链接。连续模式再分析最新证据并处理下一个问题；逐项模式在交付后停下，等待用户指示。

没有新证据时，不重复同一个无效假设：两次可比复测均不支持同一假设，应重新定位/补充证据。若受设备能力、权限或信息限制仍无法形成可验证方案，将当前问题标 blocked、说明需要的具体输入；不宣称全部解决。该规则限制盲目重试，不限制有新证据的合理迭代。

## “有效”与“全部完成”

单问题提交门槛：

- 用户场景规定的有效次数和观察期完整完成；没有用失败、超时或进程重启样本填充成功次数。
- 功能没有因修复回退；注册期间业务仍可用，销毁后资源可释放。
- 目标强持有链或分配/释放失衡已解除；预期回收的对象不再随次数持续累积，允许的有界缓存与其上限有依据。PSS 偶然下降、峰值更低或泄漏速率变慢本身不足以证明该问题已修复。
- 验证数据与源码补丁、包和设备对应；差异条件已披露，有足够证据支持归因。

单个已确认泄漏修复不要求所有 PSS 都下降。其他队列泄漏、正常缓存、Native 分配器保留和诊断干预可能继续影响进程指标，应分别解释。

队列全部 committed 后，对累计版本再跑完整批次。逐项检查旧问题未回归，最新快照与趋势无新确认问题；有新问题则入队继续。仍有 confirmed/blocked 问题时任务未完成；仅有 suspected 项时说明证据不足及观测范围，不把疑点直接宣称为泄漏，也不宣称全应用不存在任何泄漏。

## 一个问题一个 commit

提交前检查工作区和暂存区，按目标项目的提交规范操作：

- 只纳入当前问题的必要源码及确有必要的回归测试。使用显式文件路径/补丁选择，禁止 `git add .`、`git add -A` 把无关改动全部加入。
- 不混入用户先前暂存的文件/片段。暂存区已有其他内容时，必须有可靠的仅提交当前变更方法；无法隔离则说明阻塞，不清空他人暂存区。
- 检查实际将提交的 diff，运行适当检查，并确保它对应已在真机验证的代码。验证后再改功能代码必须重测，不能用旧测试结果背书。
- 提交信息描述具体根因和释放行为，并记录本问题 ID、真机测试批次/有效次数及效果摘要。原始堆数据、账号信息、token 和大型采集日志不进 commit；必要时提交脱敏的小型验证说明。
- 一个根因只保留一个成功修复 commit。失败尝试不提交到问题序列；若已提交问题后来在最终批次复发，先保留新证据并明确原验证不足。不要无授权改写已存在提交；修正提交需如实记录与原问题的关系，不伪称仍只有一个历史 commit。
- commit 后核对 SHA、文件范围和工作区；记录所有权身份符合项目规则。仅本地提交，不自动 push、创建 PR、合入、打 tag 或发布。

用户的“每个问题一个 commit”要求在问题第一次通过验证时执行；不以预先提交、多个问题 squash、重写用户历史来凑数量。
