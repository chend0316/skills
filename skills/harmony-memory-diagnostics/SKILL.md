# 鸿蒙真机内存诊断

用户指定测试场景；本 Skill 执行“编译运行 → 多次测试 → 快照分析 → 单问题修复 → 真机复测 → 单独 commit → 交付报告 → 按用户要求继续或停下”的闭环，不预设业务、应用、包名或链路开关。

## 确定本次任务

先读工作区、项目和目标模块的 `AGENTS.md`，使用项目已有构建入口。命令行工具可能在 `~/.zshenv` 配置，先检查当前 shell 是否已加载；不打印整个环境或包含密钥的构建日志。

从用户请求与已有上下文确定：

- 项目、应用 bundle、module/ability、目标真机及构建版本。
- 操作流程、完成判据、每次持续时间、重复次数、结束观察时间，以及是否比较版本或链路。
- 排查重点：总 PSS、ArkTS、Native、WebView 子进程，或已知对象链；代码仓库、分支、工作区现有修改及设备占用。

能从工程和设备只读信息获得的内容先自行查明。用户未指定业务场景时，先询问场景，不擅自录音、通话、发消息或创造其他业务数据。调用本 Skill 执行完整流程时，默认包含项目内必要编译、保留数据的覆盖安装、场景测试、源码修复和验证后的本地 commit，不逐轮重复询问。用户明确只诊断、只读或不提交时按其限制执行；项目已有权限和 SDK Review 等要求仍适用。未给重复次数时，可按场景成本先采用 5 次并说明；操作持续时间由场景需求或可观察完成状态决定，不擅自固定为录音时长。其余参数说明假设，用户指定的参数优先。

## 执行节奏

根据用户本次及此前明确要求选择：要求持续修复、自动循环或直到完成时，采用连续模式；要求每修复一个问题后停下、逐项确认或等待指示时，采用逐项模式。用户后续指示可切换模式。未指定时，完整调用本 Skill 默认连续模式，并在开始时说明；只要求处理指定单个问题时，完成该问题后停止。

每个问题独立提交后立即生成并向用户交付该问题的报告、指标表和趋势图，包含实际 commit SHA 和可访问的文件链接。每次修复报告的趋势图只展示目标对象实例数和目标对象内存占用量，具体口径见 [results-template.md](references/results-template.md)；用户另有要求时从其要求。连续模式交付后继续下一个问题；逐项模式交付后结束当前轮次，等待用户指示，不能启动下一问题的修改、构建、安装或场景测试。未清空队列时明确剩余问题和最终验收尚未完成；队列清空后仍须执行最终累计版本验收。

## 执行闭环

执行闭环前读 [references/repair-loop.md](references/repair-loop.md)，据此维护问题队列、修复前后证据和 commit 对应关系。

1. **核实环境和链路。** 用 `hdc list targets` 确认真机，后续命令显式指定 `-t <device>`。记录设备、系统、包版本、代码版本和配置；链路以日志或调试开关确认，不能只看设备名称。避免操作其他任务占用的设备。
2. **构建并运行基线版本。** 读 [references/device-run.md](references/device-run.md)，使用项目构建入口编译、覆盖安装并启动目标版本，核对实际包与源码对应。保留登录与数据；不擅自清缓存、卸载或重置应用。可复用有证据对应当前代码的既有构建，不因缓存命中就跳过版本核对。
3. **重复运行用户场景并取证。** 固定主 PID、子进程范围、采样窗口、完成判据、次数和观察时长。自动跑完本批多次场景，持续采样，并在操作前、途中与末尾的可比状态抓取堆快照。按 [references/heap-analysis.md](references/heap-analysis.md) 确认 profiler 能力和快照完整性；Native 问题补充项目已有的原生分配追踪。冷启动、预热和 GC 策略保持可比。
4. **分析并选择一个问题。** 从实际实例、跨阶段存活和强根/分配证据定位源码，给独立根因分配问题 ID。只选一个已确认且可修复的问题进入当前迭代；其他问题排队。PSS 上涨只是疑点，不直接改代码。
5. **只修复当前问题。** 依据资源所有权做最小改动，补充必要回归验证。一个根因涉及多个文件可以一起修；不夹带另一个泄漏、顺手重构或无关编译修复。构建环境问题单列，不能混进泄漏 commit。
6. **重新构建并真机复测。** 安装修复包后，用相同场景、次数、时长、配置与检查点重跑，保存独立批次。核对目标对象/资源是否按生命周期释放、原强根是否消失及功能是否正常。仍泄漏、证据不可比或功能回退时继续修当前问题，不提交成功 commit。
7. **有效后立即单独提交。** 真机验证通过后检查 diff 与暂存范围，只将当前问题的必要源码及相关测试提交为一个本地 commit，记录问题 ID、根因、验证批次和结果。不得捎带用户原有改动、其他问题、原始快照或敏感日志；不自动 push、建 PR 或合入。
8. **交付单问题报告并决定是否继续。** 按 [references/results-template.md](references/results-template.md) 生成报告、逐次指标表和趋势图，记录 commit SHA、修复前后证据、功能和未解决项，并立即向用户提供链接。按照执行节奏继续下一个问题或暂停等待用户指示；每个问题均须独立复测、提交和交付。
9. **最终验收与交付。** 队列清空后再对累计修复版本跑一批完整场景并分析快照，确认已修问题未回归且没有新的已确认泄漏；发现问题就继续闭环。使用 [references/results-template.md](references/results-template.md) 交付逐次数据、快照与根路径、问题—commit 对照、最终验证和剩余疑点。

完成范围是用户给定场景和本次可观测对象/资源内已确认的问题，不代表证明全应用永远无泄漏。遇到缺失设备、必要权限或场景信息时保留现场并明确阻塞；同一假设反复失败且没有新证据时停止盲试、报告所缺证据，不制造空 commit 或虚报完成。

## 内存采样

变量值来自本次任务，示例不代表默认测试时长：

```bash
python3 <skill-dir>/scripts/collect_memory.py \
  --device <hdc-target> --bundle <bundle-name> \
  --out <new-results-dir>/memory \
  --interval <seconds> --duration <total-seconds> --include-related
```

- 默认只采主进程；`--include-related` 另行采集 `<bundle>:<suffix>` 进程。主进程与子进程分开保留，不隐式求和。
- 若存在多个同名主进程，先核实后传 `--main-pid`，不选第一个 PID。
- 输出包含 `manifest.json`、`samples.jsonl`、`events.jsonl`、`raw/`。创建 `<out>/STOP` 可在当前采样命令返回后提前停止；输出目录必须是新目录。
- 实际采样周期取时间戳，设备慢或子进程多时可能超过请求间隔。失败和不支持的字段记录为错误或 `null`，绝不记为零。
- 脚本校验常见 HiDumper 表头。系统输出格式不同应先检查原文、调整解析并验证，不能继续套列号。

## 判断与验收

- **PSS / SwapPss** 是进程驻留指标；ArkTS PSS 可覆盖多个 VM，主线程快照只覆盖目标 VM。图上 `self_size`、联合保留大小和 PSS 不是同一口径。
- 页缓存、Native 分配器保留、JIT、首次加载和快照引入的开销都可能影响走势；总 PSS 下降也可能掩盖 ArkTS 增长。
- 页面退出后仍有对象不一定泄漏。用预期生命周期、GC 后实际实例、跨阶段 ID 和排除 weak 边的根路径共同判断；有界缓存与每次操作新增且持续存活要区分。
- 修复注册泄漏时，检查并行引用路径。只清空对象内部字段，或只删除一个服务键，可能仍被另一代理、回调或全局表持有。弱映射适用于正确的所有权关系，但不能替代订阅、定时器、原生资源的确定性释放。
- 验收分别说明功能成功、目标对象回收、稳定占用、峰值与结束增长。目标泄漏已消失不等于应用所有内存问题消失；未修复的独立问题单列。
